# Ticket 0.5 — Better Auth identity: invitation-only access, session revocation, disabled-user lockout

## What to build

A vertical identity slice on the running 0.2 compose stack: the seeded workspace owner issues an
invitation, receives a copyable single-use link (no external mail in R0, ADR-0016), the invitee
accepts it, sets a password through Better Auth, and signs in with a secure httpOnly same-site
session cookie (11 §8). Better Auth owns credentials and sessions only; identity rows live in
`core.users`/`core.actors`/`core.memberships` (06 §2.1) and authorization remains a custom
domain module (05 §2). There is no self-registration path anywhere on the server.

The governance-critical behaviour is the disable path, a restored R0 exit criterion (ADR-0011):
when a membership is set to `DISABLED`, every active session of that user is revoked server-side,
the next request with an old cookie fails with 401, sign-in returns `AUTH_ACCOUNT_DISABLED` — and
every record the user ever created remains present and attributed (06 §13: disable users, never
delete attributed history). Login success/failure, session revocation and invitation lifecycle
are written to `core.audit_events` through the append-only path (11 §12, extended per the
review's audit-gap repair; ticket 0.6 canonicalizes the action catalog). Login, invitation
acceptance and recovery endpoints are rate-limited, and no password, token or cookie value ever
reaches a log line (11 §8).

The FA-first RTL sign-in and accept-invitation screens are part of this ticket's scope but are an
explicitly 0.12-dependent sub-scope (ADR-0014): build and fully test the server side first; wire
the screens only once 0.12's DirectionProvider/token foundation exists, so no LTR/English auth UI
is ever shipped.

**Demoable when done:** `docker compose up`, seed script, one curl sequence — invite, accept,
sign in, act, disable, prove lockout and intact history — plus the audit trail listing every step.

## Blocked by

- **0.4** — identity/audit tables must exist. Server-side work can start the moment 0.4 lands.
- **0.12** — auth UI screens sub-scope only (ADR-0014). Do not hold the rest of the ticket on it.

## Acceptance criteria

- [ ] **AC1** No public signup: requests to any self-registration path return 404/405 and create
  no `core.users` row; route-table test proves the route is absent, not disabled. — Seam 2,
  `tests/integration/auth/no-public-signup.spec.ts`, `pnpm test`.
- [ ] **AC2** Invitation lifecycle: issuing creates membership `INVITED` and a hashed, expiring,
  single-use token; acceptance creates the Better Auth credential linked to `core.users` and
  flips membership to `ACTIVE` (06 §2.1). DB assertion shows no plaintext token at rest. —
  Seam 2 + DB, `tests/integration/auth/invitations.spec.ts`, `tests/db/identity/`, `pnpm test`,
  `pnpm test:db`.
- [ ] **AC3** Invalid, expired and already-consumed tokens are rejected with
  `AUTH_INVITATION_INVALID`/`AUTH_INVITATION_EXPIRED` and an audit row; a consumed token cannot
  be replayed. — Seam 2, `tests/security/auth/invitation-abuse.spec.ts`, `pnpm test`.
- [ ] **AC4** Session cookie response headers carry `HttpOnly`, `Secure` and same-site attributes
  per 11 §8. — Seam 2 header assertions, `tests/integration/auth/cookies.spec.ts`, `pnpm test`.
- [ ] **AC5** (Restored criterion, ADR-0011) Disabling a membership revokes all of the member's
  sessions (pre-disable cookie → 401 on next request), sign-in returns `AUTH_ACCOUNT_DISABLED`,
  and rows previously created by that actor remain present and attributed to them (query-level
  proof, no cascade deletes). — Seam 2 + DB, `tests/integration/auth/disable-lockout.spec.ts`,
  `tests/db/identity/history-intact.spec.ts`, `pnpm test`, `pnpm test:db`.
- [ ] **AC6** Rate limits: exceeding the configured threshold on login, invitation acceptance and
  recovery returns `AUTH_RATE_LIMITED`; limits come from typed config, not literals. — Seam 2,
  `tests/security/auth/rate-limits.spec.ts`, `pnpm test`.
- [ ] **AC7** Captured log output for failed login, invitation issue/accept and recovery contains
  no password, token, cookie or secret value (11 §8). — log-capture assertion,
  `tests/security/auth/log-redaction.spec.ts`, `pnpm test`.
- [ ] **AC8** Audit events `auth.login.succeeded`, `auth.login.failed`, `auth.session.revoked`,
  `auth.invitation.created`, `auth.invitation.accepted` are written with actor, subject and
  occurred-at through the append-only path; app DB role cannot UPDATE/DELETE them (06 §2.3). —
  DB seam, `tests/db/identity/auth-audit.spec.ts`, `pnpm test:db`.
- [ ] **AC9** (After 0.12) Sign-in and accept-invitation screens render FA-first RTL, are
  keyboard-operable and show the Persian error messages from the envelope (10 §2). — Seam 3,
  `tests/e2e/auth/`, `pnpm test:e2e`.
