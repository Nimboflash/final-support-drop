# Ticket 0.6 — Actors, roles, capabilities, scopes, approval policies and audit

## What to build

The governance core in `packages/core`: the unified actor model (11 §2), the seven canonical
roles and the capability list (11 §3-4) plus the new `RAW_RESPONSE_READ` capability, scoped
role/capability assignments, a single `authorize()` evaluation service that records the acted-as
role, the approval policy/request/decision domain services, and the append-only audit writer.
Everything is server-side domain logic in shared packages — no business rule in a route handler
(05 §1) — and it is exactly the service layer ticket 0.16's approval endpoints will call
(ADR-0014).

Approvals are the most governance-critical state in the system, so ADR-0013 is applied literally
here, at two layers each: `minimum_approvals: N` is satisfied only by N **distinct HUMAN actors**
(a partial unique DB constraint on approve-decisions per request plus a service check), only
HUMAN actors may decide (service check plus DB trigger/check), `DISTINCT_REVIEWER_REQUIRED`
excludes the subject creator by comparing actor identity, never roles or sessions (11 §6.1), and
the runtime command set contains no `APPROVE_GATE`/`REQUEST_CHANGES`/`ESCALATE_GATE` verbs — the approval
request/decision path is the only write path. Approval requests pin the exact immutable subject
version; a new version means a new request (06 §2.2).

The audit writer implements the 11 §12 record minimum and closes the review's audit gaps: the
auth events emitted by 0.5 are canonicalized into the catalog, every authorization denial is
audited (`authz.denied`), and reads of the restricted raw-response namespace are declared a
capability-gated, audited action (`raw_response.read`) even though no read endpoint ships in R0
— the gate exists before the door does. `core.audit_events` and `core.approval_events` are
append-only at the database-permission level (06 §2.3), not merely by convention.

**Demoable when done:** a seeded workspace with two humans and one machine actor where a
two-approval policy demonstrably cannot be satisfied by one person twice, cannot be decided by
the machine actor, and every attempt — allowed or denied — is visible as an ordered, immutable
audit trail queried straight from PostgreSQL.
