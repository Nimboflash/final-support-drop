## What to build

The persistence half of the R0 tracer bullet: every durable structure the Release 0 vertical
demo (15 §2) touches — identity, approvals, audit, the Project/Program/Lens hierarchy, workflow
definitions and runs, and the registries that run manifests freeze — exists as reviewed SQL with
its invariants enforced by the database itself, not by hidden edit buttons (06 §11).

Build the `core` and `studio` schemas per (06 §2, §3, §9) with the 06 §1 conventions applied
uniformly. Apply the repairs as settled decisions: the run-level status enum and stage enum come
verbatim from the Ticket 0.3 contracts (ADR-0012); node definitions carry the manual_fallback
column so published definitions can legally authorize human input on automated stages
(ADR-0012); and the approval tables enforce ADR-0013 in the schema — a partial unique index
guaranteeing one decision per actor per approval request (which is what makes
minimum_approvals = N mean N distinct people) and a trigger rejecting any decision event whose
actor is not HUMAN. Machines never hold approval authority becomes a database fact.

Per ADR-0015, the registries that (07 §6) requires run manifests to freeze get real versioned
tables here: constitution, rule, prompt and example registries with publish status and unique
version keys. `programs.constitution_version_id` finally has an FK target. Executor/validator identity
stays code-version + checksum frozen inside run_manifests, with one lightweight durable
record: `studio.executor_registrations` (package, code version, checksum, status
`ACTIVE|RETIRED`) per ADR-0015 D4, so publish-time "exists and is active" (07 §13) validation
has rows to check — 0.16's publish engine and the testing-strategy §3.2 scenarios depend on
it. Publish-flow services over these tables are Ticket 0.8; only schema lands here.

Immutability uses layers 2 and 3 of (06 §11): triggers or restricted policies on append-only
and published rows, application-role grants that physically lack UPDATE/DELETE on
audit/approval/run-event/run-manifest tables, and negative tests that attempt the prohibited
writes through the repository seam and raw SQL. Scope discipline: Machine 01-05 entity tables
stay out (their subsystem tickets own them), which keeps this ticket inside a single
fresh-context session while still satisfying the ADR-0011 R0 exit restoration — Project and
Program rows exist, versioned, ready for the 0.7/0.16 API surface.

**Demoable when done:** `pnpm test:db` green; a reviewer can watch a raw SQL
`UPDATE core.approval_events ...` fail, watch a second APPROVED decision by the same actor fail,
and diff the committed migration SQL.

## Acceptance criteria

- [ ] **AC-1** Migrations apply cleanly from an empty database AND from the previous committed migration state (16 §12); `pnpm test:db` runs the full suite green (14 §3 layer 2). *Seam: db migration tests.*
- [ ] **AC-2** Introspection tests verify 06 §1 conventions on every created table: created_at/updated_at/row_version on mutable business tables, workspace_id direct or via immutable parent, FKs present, correct core/studio schema placement. *Seam: db introspection tests.*
- [ ] **AC-3** Negative tests prove UPDATE and DELETE on core.audit_events, core.approval_events, studio.run_events and studio.run_manifests are rejected both for the application role (missing grant) and via trigger for privileged roles (06 §2.3, §11). *Seam: db constraint tests + repository seam.*
- [ ] **AC-4** After a workflow_definition_version reaches PUBLISHED, UPDATE/DELETE on the version row and its node/edge rows are rejected; DRAFT rows remain editable (06 §9.1). *Seam: db constraint tests.*
- [ ] **AC-5** ADR-0013 constraints hold: a second decision event by the same actor on the same approval_request is rejected by the unique index; a decision event whose actor has actor_type MACHINE or SERVICE is rejected by trigger; a test documents that N-approval quorums therefore require N distinct human actors. *Seam: db constraint tests.*
- [ ] **AC-6** The database stage and run status enum labels are compared 1:1 against the Ticket 0.3 contract enums in a test — any drift fails (ADR-0012). *Seam: db introspection tests vs packages/contracts.*
- [ ] **AC-7** The five ADR-0015 enum types exist with exactly the ADR-0015 labels; projects.status, programs.status and weekly_lenses.status columns use them; requests/calendar_items types exist unused, reserved for their owning tickets. *Seam: db introspection tests.*
- [ ] **AC-8** Constitution/rule/prompt/example registry tables exist with version rows, publish status and unique version constraints; programs.constitution_version_id FK resolves to a constitution version row; inserting a program with a dangling constitution_version_id fails (ADR-0015). *Seam: db constraint tests.*
- [ ] **AC-9** weekly_lenses rejects planned_end_at <= planned_start_at, and rejects status APPROVED while current_context_artifact_id or concept_bible_version_id is NULL (06 §3.4; artifact FK itself deferred to 0.7). *Seam: db constraint tests.*
- [ ] **AC-10** Unique (run_id, sequence_number) on run_events and unique (run_id, idempotency_key) on run_commands are enforced (06 §9.2). *Seam: db constraint tests.*
- [ ] **AC-11** The 06 §12 indexing baseline applicable to created tables exists (all FKs; (workspace_id, status, updated_at desc) on list entities; (run_id, sequence_number); partial indexes for open approvals/active runs/current versions), verified by introspection. *Seam: db introspection tests.*
- [ ] **AC-12** One application ID strategy is used by every created table (06 §1), asserted by an introspection test over ID column types/defaults and documented in packages/db. *Seam: db introspection tests.*
