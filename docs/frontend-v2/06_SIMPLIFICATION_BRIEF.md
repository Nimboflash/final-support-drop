# DROP Studio — Simplification & Restructure Brief

> این سند، دستور اجرایی بازطراحی پنل Studio در DROP OS است. آن را به‌عنوان منبع اصلی تصمیم‌گیری برای اجرای تغییرات در Cloud استفاده کن.

## 1. مأموریت

پنل فعلی Studio را از یک داشبورد پیچیده و فرایندمحور به یک فضای کاری ساده برای ساخت، بررسی و برنامه‌ریزی محتوا تبدیل کن.

مسیر ذهنی و عملیاتی اصلی کاربر باید این باشد:

```text
شروع کانسپت → انتخاب کانسپت → تولید و بهبود محتوا → تأیید خروجی → برنامه‌ریزی در تقویم
```

مدل کوتاه محصول:

```text
Concept → Content → Output → Calendar
```

کاربر نباید برای انجام کار اصلی مجبور باشد ساختار فنی سیستم، نسخه‌ها، وابستگی‌ها، تیکت‌ها یا گردش‌کار داخلی را بفهمد.

---

## 2. قواعد قطعی اجرا

1. ظاهر و ساختار را ساده کن؛ قابلیت‌های اصلی و داده‌های موجود را بی‌دلیل حذف نکن.
2. ابتدا کد و ساختار فعلی پروژه را بررسی کن و سپس تغییر بده. از بازنویسی کامل بدون نیاز خودداری کن.
3. بک‌اند، قراردادهای داده و مسیرهای فعلی را تا جای ممکن حفظ کن؛ پیچیدگی را در لایه رابط پنهان یا تجمیع کن.
4. هیچ متن فنی، شناسه داخلی یا نام تیکت در رابط نهایی نمایش داده نشود.
5. RTL و زبان فارسی، رفتار موبایل و دسترس‌پذیری باید حفظ شوند.
6. هیچ تغییر نامرتبطی خارج از Studio انجام نده.
7. داده‌های mock و حالت‌های فعلی را برای تست سناریوهای مختلف نگه دار.
8. قبل از پایان کار، تمام مسیر اصلی را روی دسکتاپ و موبایل تست کن.

### مواردی که نباید در UI کاربر دیده شوند

- شناسه‌هایی مانند `p1`، `c1-v1`، `o2` و مشابه آن‌ها
- نام یا شماره تیکت‌هایی مانند `P4` و `P6`
- پیام‌هایی مانند «از گیت‌وی خوانده می‌شود» یا «اجرای ماشین شبیه‌سازی شده است»
- اصطلاحات فنی مانند dependency، target version، package build و workflow state
- شمارنده‌های داخلی مانند «۲ از ۴ مورد الزامی» بدون توضیح انسانی

اطلاعات فنی ضروری می‌تواند در لاگ توسعه یا پنل debug باقی بماند، اما نه در تجربه اصلی.

## 3. مسئله فعلی

در نسخه فعلی:

- صفحه‌ی نمای کلی هم‌زمان شمارنده‌ها، هشدارها، پروژه‌ها، مراحل پروژه و برنامه دو هفته آینده را نشان می‌دهد.
- هر پروژه هفت بخش داخلی دارد: خلاصه، کانسپت‌ها، محتوا و تحقیق، خروجی نهایی، برنامه، گردش کار و تاریخچه.
- برای هر پروژه یک نوار پنج‌مرحله‌ای در چند نقطه تکرار می‌شود.
- تصمیم‌گیری درباره کانسپت هم در پروژه و هم در صفحه «بررسی‌ها» انجام می‌شود.
- «خروجی‌ها» بین محتواها و نسخه‌های بسته تقسیم شده و زبان آن با زبان ذهنی کاربر هم‌راستا نیست.
- کار اصلی کاربر، یعنی شروع یک ایده و ادامه دادن آن، زیر اطلاعات عملیاتی پنهان شده است.

نتیجه: رابط فعلی وضعیت سیستم را توضیح می‌دهد، نه اینکه کاربر را در مسیر ساخت محتوا هدایت کند.

## 4. مدل مفهومی جدید

### Program

گروه یا زمینه‌ی بالادستی برای پروژه‌ها. Program نباید یک مرحله از گردش‌کار باشد و لازم نیست در ناوبری اصلی دیده شود. در صورت نیاز فقط به‌صورت فیلتر یا metadata نمایش داده شود.

### Project

ظرف کاری و context مشترک برای کانسپت‌ها، محتواها و خروجی‌ها. Project یک «مقصد اصلی» در ناوبری نیست.

کاربر می‌تواند پروژه را از کارت‌های نمای کلی یا selector بالای صفحات باز کند، اما پس از ورود مستقیماً با کانسپت، محتوا یا خروجی کار می‌کند.

### Concept

اولین واحد قابل مشاهده و تصمیم‌گیری. هر بار شروع، معمولاً ۳ تا ۴ کانسپت تولید می‌کند.

### Content

هر آیتم محتوایی که از یک کانسپت انتخاب‌شده تولید می‌شود؛ مانند Editorial، Film، Music یا Landing. هر محتوا همیشه باید به کانسپت مادر خود متصل باشد.

### Output

مجموعه سازمان‌یافته‌ی محتواهای تأییدشده یک کانسپت. در UI فقط از واژه «خروجی» استفاده کن؛ اصطلاح «بسته» یا Package را از رابط اصلی حذف کن.

### Calendar Item

یک خروجی تأییدشده که تاریخ انتشار گرفته است. آیتم تقویم باید پروژه، کانسپت، تمام محتواها و متریال‌های مرتبط را همراه خود داشته باشد.

## 5. معماری اطلاعات و ناوبری

ناوبری اصلی Studio:

1. نمای کلی
2. کانسپت‌ها
3. محتوا
4. خروجی‌ها
5. تقویم
6. Engine

تنظیمات را از ناوبری اصلی جدا کن و داخل منوی ثانویه یا پروفایل قرار بده.

`Engine` یک نمای عملیاتی و بصری از جریان پشت صحنه است. این تب باید مستقل از فلوی محتوایی باشد تا جزئیات اجرای workflow دوباره وارد صفحات کانسپت، محتوا و خروجی نشوند.

### تغییر نام و ادغام بخش‌ها

| فعلی | جدید | تصمیم |
|---|---|---|
| پروژه‌ها | کانسپت‌ها | پروژه context است؛ مقصد اصلی کاربر کانسپت است |
| بررسی‌ها | محتوا | تب‌های «کانسپت‌ها / محتوا» حذف شوند |
| خروجی‌ها / نسخه‌های بسته | خروجی‌ها | همه در یک مدل ساده ادغام شوند |
| تقویم و برنامه | تقویم | نام کوتاه و روشن |
| برنامه داخلی پروژه | ادغام در تقویم | صفحه مستقل حذف شود |
| گردش کار | Engine | workflow به‌صورت گراف زنده و قابل فهم نمایش داده شود |
| تاریخچه | منوی ثانویه | فقط در صورت نیاز و خارج از مسیر اصلی |

### اصل ناوبری

هر صفحه باید فقط یک سؤال اصلی را جواب بدهد:

- نمای کلی: الان چه چیزی به توجه من نیاز دارد؟
- کانسپت‌ها: چه ایده‌هایی داریم و کدام را ادامه بدهم؟
- محتوا: برای کانسپت‌های انتخاب‌شده چه محتواهایی آماده یا ناقص‌اند؟
- خروجی‌ها: چه چیزی آماده تأیید و انتشار است؟
- تقویم: چه چیزی چه زمانی منتشر می‌شود؟
- Engine: هر پروژه یا اجرای فعال اکنون در کدام بخش workflow قرار دارد؟

## 6. فلوی اصلی کاربر

### مرحله 1 — شروع

کاربر از دکمه‌ی اصلی «شروع کانسپت جدید» وارد یک composer مشابه شروع چت جدید می‌شود.

Composer باید همه حالت‌ها را یک‌جا پوشش دهد و قبل از شروع، کاربر را مجبور به انتخاب mode نکند.

ورودی‌های ممکن:

- نوشتن درخواست یا brief
- افزودن فایل
- افزودن لینک یا رفرنس
- انتخاب ایده‌ها یا کانسپت‌های قبلی
- شروع بدون ورودی بر اساس context موجود پروژه

CTA اصلی: `تولید کانسپت‌ها`

گزینه ثانویه: `بدون ورودی شروع کن`

رفتار مورد انتظار:

1. کاربر پروژه/context را انتخاب می‌کند یا یک پروژه جدید می‌سازد.
2. ورودی دلخواه را می‌دهد؛ ورودی اجباری نیست.
3. سیستم فرایند تولید را آغاز می‌کند.
4. یک وضعیت loading ساده و انسانی نمایش داده می‌شود.
5. بین ۳ تا ۴ کانسپت جدید به فهرست اضافه می‌شود.

پیام‌های مناسب loading:

- «در حال بررسی رفرنس‌ها…»
- «در حال ساخت چند مسیر کانسپت…»
- «کانسپت‌ها تا لحظاتی دیگر آماده‌اند.»

### مرحله 2 — بررسی و انتخاب کانسپت

کانسپت‌های تولیدشده به شکل کارت نمایش داده شوند. کاربر می‌تواند هر کارت را باز کند، درباره آن گفت‌وگو کند، آن را بهتر کند یا برای تولید محتوا انتخاب کند.

### مرحله 3 — تولید محتوا

کانسپت‌های انتخاب‌شده وارد صفحه محتوا می‌شوند. محتواها در همان صفحه و زیر کانسپت مادر گروه‌بندی می‌شوند.

### مرحله 4 — ساخت خروجی

محتواهای تأییدشده یک کانسپت در یک خروجی منسجم کنار هم قرار می‌گیرند. کاربر خروجی را مرور و تأیید می‌کند.

### مرحله 5 — برنامه‌ریزی

خروجی تأییدشده وارد سینی «بدون تاریخ» تقویم می‌شود. کاربر برای آن تاریخ تعیین می‌کند و سپس آیتم در نمای ماه/هفته/فهرست دیده می‌شود.

## 7. مشخصات صفحات

## 7.1 نمای کلی

### هدف

یک landing page سبک برای شروع کار و دیدن موارد نیازمند اقدام.

### ساختار

1. عنوان کوتاه و CTA برجسته «شروع کانسپت جدید»
2. بخش «نیازمند اقدام شما»
3. پروژه‌های باز به شکل کارت‌های ساده
4. در صورت نیاز، خروجی‌های نزدیک به انتشار به شکل یک ردیف کوچک

### کارت پروژه

نمایش دهد:

- نام پروژه
- Program یا زمینه، در صورت وجود
- آخرین فعالیت
- فقط یک پیام عملیاتی انسانی
- CTA برای ادامه

نمونه پیام عملیاتی:

- «۳ کانسپت جدید آماده بررسی است.»
- «۲ محتوا به تأیید شما نیاز دارد.»
- «خروجی آماده برنامه‌ریزی است.»
- «هنوز کانسپتی برای این پروژه ساخته نشده.»

### حذف شود

- چهار کارت شمارنده‌ی بزرگ فعلی
- نوار پنج مرحله‌ای داخل هر کارت پروژه
- عبارت «۲ از ۴ مورد الزامی تأیید شده»
- بخش «دو هفته آینده»
- هشدارهای تکراری وابستگی با زبان فنی

اگر یک مانع واقعی وجود دارد، آن را با زبان انسانی در «نیازمند اقدام شما» نمایش بده.

## 7.2 صفحه کانسپت‌ها

### هدف

مرکز شروع، مرور و انتخاب ایده‌ها.

### Header

- عنوان «کانسپت‌ها»
- selector پروژه
- دکمه «شروع کانسپت جدید»
- جست‌وجو فقط اگر تعداد داده‌ها زیاد است

### گروه‌بندی

کانسپت‌ها را بر اساس پروژه گروه‌بندی کن یا با فیلتر پروژه نمایش بده. از ساختن لایه ناوبری جداگانه برای Program خودداری کن.

### کارت کانسپت

فقط شامل:

- عنوان کانسپت
- توضیح کوتاه، حداکثر ۲ تا ۳ خط
- تاریخ تولید
- تصویر/thumbnail در صورت وجود
- برچسب بسیار ساده، فقط اگر برای تصمیم کاربر مفید است

CTA روی کارت: `باز کردن کانسپت`

### وضعیت‌ها

وضعیت‌های قابل نمایش را به حداقل برسان:

- جدید
- انتخاب‌شده
- کنار گذاشته‌شده

«در حال بررسی»، «درخواست بازنگری»، «نسخه هدف» و وضعیت‌های مشابه نباید به‌عنوان فرایند اصلی دیده شوند. بهبود کانسپت از طریق گفت‌وگو و ایجاد revision انجام می‌شود.

---

## 7.3 جزئیات کانسپت

### Layout پیشنهادی

در دسکتاپ:

- ستون اصلی: سند کانسپت
- ستون کناری: گفت‌وگو و اقدامات

در موبایل:

- ابتدا سند
- سپس منابع و منشأ
- composer چت به شکل sticky در پایین

### بخش‌های سند

- عنوان
- خلاصه
- ایده اصلی
- دلیل و منطق شکل‌گیری
- جهت بصری یا محتوایی
- رفرنس‌ها و ورودی‌های اولیه
- تاریخ ایجاد و آخرین به‌روزرسانی

### گفت‌وگو

کاربر باید بتواند مستقیماً بنویسد:

- «این مسیر را مینیمال‌تر کن.»
- «سه نام جایگزین بده.»
- «بر اساس رفرنس دوم ادامه بده.»
- «نسخه‌ای با لحن متفاوت بساز.»

پاسخ‌ها باید revision جدید ایجاد کنند، اما مدیریت نسخه نباید به تجربه غالب تبدیل شود. در صورت نیاز، تاریخچه نسخه‌ها از یک منوی کوچک قابل دسترسی باشد.

### اقدامات اصلی

- `انتخاب برای تولید محتوا`
- `بهبود کانسپت`
- `کنار گذاشتن`

از نمایش هم‌زمان تعداد زیادی دکمه تأیید/رد/اصلاح خودداری کن.

## 7.4 صفحه محتوا

### هدف

ساخت و تکمیل محتوا برای کانسپت‌های انتخاب‌شده.

### ساختار

- selector یا فیلتر پروژه
- هر کانسپت به‌عنوان یک section یا parent card
- محتواهای مربوط به آن کانسپت درون همان section

### کارت محتوا

- نوع محتوا: Editorial / Film / Music / Landing
- عنوان
- پیش‌نمایش کوتاه
- وضعیت ساده
- تعداد یا خلاصه منابع، فقط در صورت کاربرد
- CTA «باز کردن و ویرایش»

### صفحه یا drawer جزئیات محتوا

- متن کامل محتوا
- منابع
- editor مستقیم
- گفت‌وگو برای بهبود
- اقدام اصلی «تأیید محتوا»
- اقدام ثانویه «نیاز به تغییر»

اگر منبع لازم در دسترس نیست، به‌جای disabled کردن تمام دکمه‌ها فقط یک پیام عملیاتی روشن نمایش بده:

> برای نهایی‌کردن این محتوا یک منبع معتبر لازم است.

CTA پیشنهادی: `افزودن منبع`

### حذف شود

- تب جداگانه کانسپت/محتوا در «بررسی‌ها»
- صفحه review موازی
- پوشش تحقیق به‌عنوان یک بخش فنی و جدا از محتوا
- نسخه قفل‌شده با شناسه داخلی

## 7.5 صفحه خروجی‌ها

### هدف

مرور و تأیید مجموعه کامل محتوای هر کانسپت پیش از برنامه‌ریزی.

### کارت خروجی

- نام پروژه
- نام کانسپت
- خلاصه محتواهای موجود
- وضعیت انسانی
- تاریخ آخرین تغییر
- CTA «بررسی خروجی»

### جزئیات خروجی

- خلاصه کانسپت
- تمام محتواها و متریال‌های مرتبط
- پیش‌نمایش منسجم خروجی
- موارد ناقص با توضیح روشن
- اقدام اصلی «تأیید خروجی»
- پس از تأیید: «ارسال به تقویم»

### وضعیت‌ها

- در حال تکمیل
- آماده تأیید
- تأییدشده
- برنامه‌ریزی‌شده

### حذف شود

- تب‌های «محتواها» و «نسخه‌های بسته»
- اصطلاح «بسته» در UI
- لینک‌هایی که فقط شناسه داخلی نمایش می‌دهند

## 7.6 صفحه تقویم

### هدف

برنامه‌ریزی واقعی و تعاملی خروجی‌های تأییدشده. این صفحه نباید صرفاً یک فهرست تاریخ‌دار با ظاهر تقویم باشد؛ باید رفتار و ساختار یک calendar کامل را داشته باشد.

### الزامات تقویم واقعی

- grid واقعی ماه با روزهای ماه قبل/بعد، روز جاری و انتخاب روز
- navigation ماه/هفته قبل و بعد
- دکمه `امروز`
- عنوان بازه زمانی جاری
- نمایش eventها داخل خانه روز مربوط
- نمای هفته با ستون روزها و بازه‌های زمانی، در صورت وجود زمان انتشار
- نمای فهرست/Agenda برای مرور سریع
- کلیک روی روز برای دیدن یا افزودن برنامه مجاز
- کلیک روی event برای باز کردن جزئیات
- جابه‌جایی event به تاریخ دیگر با drag & drop، همراه با روش جایگزین انتخاب تاریخ
- حفظ تاریخ و وضعیت پس از refresh
- نمایش صحیح locale فارسی، RTL و timezone پروژه

از یک calendar component واقعی و قابل نگهداری استفاده کن. ابتدا dependencyهای موجود repository را بررسی و همان‌ها را reuse کن. اگر کتابخانه تقویم مناسبی وجود ندارد، یک گزینه استاندارد و سازگار با React انتخاب کن؛ از ساختن یک grid نمایشی بدون منطق calendar خودداری کن.

### نماها

- ماه
- هفته
- فهرست

این سه نما می‌توانند حفظ شوند.

نمای پیش‌فرض دسکتاپ `ماه` است. در موبایل آخرین نمای انتخاب‌شده حفظ شود و `فهرست` یا نمای روزانه می‌تواند گزینه کاربردی‌تر پیش‌فرض باشد، اما کاربر همچنان باید بتواند ماه را ببیند.

### سینی بدون تاریخ

خروجی‌های تأییدشده و بدون تاریخ در یک سینی ساده نمایش داده شوند. هر آیتم باید نام پروژه، کانسپت و نوع محتواهای همراه را نشان دهد.

کاربر باید بتواند:

- تاریخ انتخاب کند
- تاریخ را تغییر دهد
- جزئیات خروجی را باز کند

در صورت امکان drag & drop را به‌عنوان قابلیت کمکی اضافه کن، اما flow نباید به آن وابسته باشد.

### آیتم تقویم

با باز شدن آیتم:

- پروژه و کانسپت
- محتواها و متریال‌ها
- تاریخ انتشار
- وضعیت آماده‌بودن
- لینک به خروجی اصلی

نمایش داده شود.

### جزئیات تعامل

- آیتم‌های تقویم بر اساس پروژه قابل فیلتر باشند.
- رنگ event فقط برای تشخیص سریع پروژه یا نوع خروجی استفاده شود و متن وضعیت نیز وجود داشته باشد.
- تغییر تاریخ باید optimistic feedback داشته باشد و در صورت خطا به تاریخ قبلی برگردد.
- برای eventهای چندروزه، span صحیح در grid نمایش داده شود.
- اگر ساعت انتشار وجود دارد، در نمای هفته و فهرست نمایش داده شود.
- تقویم در desktop و mobile نباید به یک لیست ثابت تبدیل شود؛ رفتارهای انتخاب تاریخ، navigation و event detail باید واقعی باشند.

## 7.7 صفحه Engine

### هدف

نمایش بصری workflow واقعی هر پروژه یا run، از ورودی اولیه تا قرارگرفتن خروجی در تقویم. کاربر باید در یک نگاه بفهمد چه کاری کامل شده، چه کاری در حال اجراست، چه چیزی منتظر تصمیم اوست و خطا کجاست.

### جایگاه

- یک تب مستقل با نام `Engine` در ناوبری Studio
- route پیشنهادی: `/studio/engine`
- این صفحه operational است و نباید جای صفحات کانسپت، محتوا یا خروجی را بگیرد.

### تکنولوژی و کامپوننت‌ها

- از React و componentهای موجود `shadcn/ui` برای shell، toolbar، badge، tooltip، drawer، tabs و جزئیات node استفاده کن.
- برای گراف workflow، ابتدا dependencyهای موجود را بررسی کن. اگر React Flow یا نسخه جدید آن موجود است، همان را reuse کن؛ در غیر این صورت از `@xyflow/react` استفاده کن.
- nodeها به‌صورت custom React component ساخته شوند و styling آن‌ها با design tokenها و componentهای موجود هماهنگ باشد.
- داده workflow از state واقعی برنامه ساخته شود؛ گراف hard-coded صرفاً نمایشی قابل قبول نیست. mock data فقط برای حالت توسعه و تست مجاز است.

### ساختار صفحه

1. toolbar بالای صفحه
2. canvas گراف workflow
3. پنل جزئیات node یا run در کنار صفحه
4. legend کوچک وضعیت‌ها

### Toolbar

- انتخاب پروژه
- انتخاب run، اگر یک پروژه چند اجرای جدا دارد
- وضعیت کلی run
- زمان آخرین به‌روزرسانی
- `Fit view`
- refresh در صورت نبود live update

### مسیر پایه workflow

```text
Start / Inputs
  → Generate Concepts
  → Human Concept Selection
  → Research
  → Generate Content
  → Human Content Approval
  → Assemble Output
  → Human Output Approval
  → Schedule
  → Done
```

شاخه‌های Editorial، Film، Music و Landing می‌توانند در مرحله تولید محتوا به‌صورت parallel node نمایش داده شوند و قبل از Assemble Output دوباره به هم برسند.

### وضعیت nodeها

- `waiting` — هنوز شروع نشده
- `running` — در حال اجرا
- `needs_attention` — منتظر اقدام کاربر
- `completed` — کامل شده
- `failed` — با خطا متوقف شده
- `skipped` — در این run لازم نبوده

وضعیت active علاوه بر رنگ باید با label، icon یا animation ملایم مشخص شود. animation نباید مزاحم یا دائماً چشمک‌زن باشد.

### اطلاعات داخل node

- نام انسانی مرحله
- وضعیت
- زمان شروع یا مدت اجرا، در صورت وجود
- تعداد نتیجه‌ها یا خلاصه خروجی، در صورت مفید بودن

شناسه خام، payload کامل و جزئیات فنی داخل node نمایش داده نشوند.

### پنل جزئیات node

با انتخاب node، یک side panel یا drawer با این اطلاعات باز شود:

- توضیح مرحله
- وضعیت و زمان‌بندی
- ورودی‌های قابل فهم
- خروجی یا نتیجه مرحله
- خطا با متن انسانی، در صورت وجود
- لینک به صفحه مرتبط؛ مانند باز کردن کانسپت یا محتوای نیازمند تأیید

Engine در نسخه اول read-first باشد. عملیات destructive یا کنترل‌های پیچیده مانند skip اجباری و تغییر دستی state اضافه نشوند. اگر retry از قبل در سیستم وجود دارد، فقط برای node شکست‌خورده و با confirmation مناسب نمایش داده شود.

### تعامل با گراف

- pan و zoom
- fit view
- انتخاب node
- highlight مسیر فعال
- tooltip برای اطلاعات کوتاه
- عدم امکان جابه‌جایی تصادفی nodeها توسط کاربر، مگر اینکه هدف آینده ویرایش workflow باشد
- layout خودکار و پایدار تا با refresh جای nodeها بی‌دلیل تغییر نکند

### Responsive

- در desktop، canvas و پنل جزئیات کنار هم قرار بگیرند.
- در mobile، canvas تمام عرض باشد و جزئیات در bottom sheet باز شود.
- کنترل‌های zoom و fit view در دسترس بمانند.
- گراف در موبایل قابل pan باشد و صفحه را دچار scroll افقی ناخواسته نکند.

### Empty و Error State

اگر پروژه‌ای انتخاب نشده:

> یک پروژه را انتخاب کنید تا جریان اجرای آن را ببینید.

اگر run وجود ندارد:

> هنوز جریانی برای این پروژه شروع نشده است.

اگر داده workflow ناقص است، بخش سالم گراف نمایش داده شود و خطا به‌صورت پیام انسانی در همان node یا پنل جزئیات دیده شود.

## 8. ساختار پروژه داخل رابط

صفحه داخلی پروژه با هفت تب فعلی حذف یا بسیار کوچک شود.

اگر routeهای فعلی برای سازگاری لازم‌اند، آن‌ها را نگه دار اما به صفحات جدید redirect یا map کن:

| مسیر فعلی | مقصد پیشنهادی |
|---|---|
| `/studio/projects` | `/studio/concepts` یا نمای کانسپت‌ها با فیلتر پروژه |
| `/studio/projects/:id/overview` | نمای کلی فیلترشده روی پروژه |
| `/studio/projects/:id/concepts` | کانسپت‌ها با پروژه انتخاب‌شده |
| `/studio/projects/:id/content` | محتوا با پروژه انتخاب‌شده |
| `/studio/projects/:id/outputs` | خروجی‌ها با پروژه انتخاب‌شده |
| `/studio/projects/:id/plan` | تقویم با پروژه انتخاب‌شده |
| `/studio/projects/:id/workflow` | `/studio/engine?project=:id` |
| `/studio/projects/:id/activity` | history ثانویه، نه تب اصلی |
| `/studio/reviews` | `/studio/content` |
| `/studio/calendar` | حفظ شود |
| `/studio/engine` | route جدید برای workflow graph |

نام و route دقیق را بر اساس معماری فعلی repository انتخاب کن؛ هدف، حفظ سازگاری و حذف مسیرهای تکراری از UI است.

## 10. اصول طراحی و محتوا

### سلسله‌مراتب

- در هر صفحه فقط یک CTA اصلی وجود داشته باشد.
- اطلاعات تصمیم‌ساز بالاتر از metadata قرار بگیرد.
- status رنگی جای متن روشن را نگیرد.
- جزئیات ثانویه در drawer، accordion یا منوی بیشتر قرار بگیرند.

### زبان

- کوتاه، انسانی و عملیاتی
- از واژه‌های «کانسپت»، «محتوا»، «خروجی» و «تقویم» به‌صورت ثابت استفاده شود.
- از نام‌های هم‌معنا برای یک مفهوم استفاده نکن.
- متن دکمه باید نتیجه عمل را بگوید.

نمونه:

- خوب: «انتخاب برای تولید محتوا»
- مبهم: «ادامه»
- خوب: «افزودن منبع»
- فنی: «بررسی وابستگی»

### تراکم

- کارت‌ها فقط اطلاعات لازم برای تصمیم همان لحظه را نشان دهند.
- فیلترها تا زمانی که حجم داده نیاز ایجاد نکرده، collapsed یا حذف شوند.
- نوار مرحله‌ای تکرارشونده حذف شود.

### Responsive

- طراحی mobile-first و RTL باشد.
- CTA اصلی روی موبایل در دسترس و واضح بماند.
- گفت‌وگو در جزئیات کانسپت و محتوا در موبایل به پایین صفحه منتقل شود.
- هیچ کارت یا جدول نیازمند scroll افقی نباشد. pan داخل canvas کنترل‌شده‌ی Engine از این قاعده مستثناست و نباید باعث scroll افقی خود صفحه شود.

### Accessibility

- همه کنترل‌ها label قابل فهم داشته باشند.
- فقط از رنگ برای بیان وضعیت استفاده نشود.
- focus state واضح باشد.
- modal/drawer با کیبورد و Escape قابل کنترل باشد.
- ترتیب خواندن RTL و heading hierarchy صحیح باشد.

## 11. حالت‌های ضروری

برای هر صفحه حداقل این حالت‌ها را طراحی و پیاده‌سازی کن:

- loading
- empty
- error
- partial data
- ready
- نیازمند اقدام کاربر

### Empty stateهای پیشنهادی

کانسپت‌ها:

> هنوز کانسپتی ساخته نشده. اولین مسیر را شروع کنید.

محتوا:

> ابتدا یک کانسپت را برای تولید محتوا انتخاب کنید.

خروجی‌ها:

> پس از تأیید محتواها، خروجی کامل اینجا ساخته می‌شود.

تقویم:

> هنوز خروجی تأییدشده‌ای برای برنامه‌ریزی وجود ندارد.

### خطا

پیام خطا باید بگوید چه اتفاقی افتاده و کاربر چه کاری می‌تواند انجام دهد. خطای خام API یا stack trace در UI نمایش داده نشود.

## 12. مدل وضعیت ساده‌شده

پیچیدگی state داخلی می‌تواند حفظ شود، اما UI باید آن را به وضعیت‌های محدود و انسانی map کند.

### Concept

```text
generating → new → selected | set_aside
```

### Content

```text
draft → needs_input | ready_for_review → approved
```

### Output

```text
assembling → ready_for_approval → approved → scheduled
```

هرجا state داخلی بیشتری وجود دارد، یک mapping مرکزی بساز تا label، توضیح و CTA متناظر از یک منبع واحد دریافت شوند.

## 14. معیارهای پذیرش

پیاده‌سازی زمانی کامل است که:

1. کاربر از نمای کلی با یک CTA واضح بتواند تولید کانسپت را شروع کند.
2. شروع با prompt، فایل، لینک، رفرنس قبلی یا بدون ورودی ممکن باشد.
3. هر شروع ۳ تا ۴ کانسپت قابل مرور تولید یا شبیه‌سازی کند.
4. کارت کانسپت فقط عنوان، توضیح، تاریخ و preview مفید را نشان دهد.
5. جزئیات کانسپت یک سند خوانا و فضای گفت‌وگو برای بهبود داشته باشد.
6. کاربر بتواند کانسپت را برای تولید محتوا انتخاب یا کنار بگذارد.
7. صفحه محتوا فقط محتواها را نشان دهد و آن‌ها را زیر کانسپت مادر گروه‌بندی کند.
8. هر محتوا قابلیت مشاهده، ویرایش، بهبود، افزودن منبع و تأیید داشته باشد.
9. صفحه Review موازی یا تب Concept Review وجود نداشته باشد.
10. خروجی‌های هر کانسپت به شکل یک مجموعه منسجم قابل مرور و تأیید باشند.
11. خروجی تأییدشده بتواند وارد سینی بدون تاریخ تقویم شود.
12. تقویم اطلاعات پروژه، کانسپت و متریال‌های خروجی را حفظ کند.
13. نمای کلی فاقد نوار پنج‌مرحله‌ای و بخش «دو هفته آینده» باشد.
14. هیچ شناسه یا متن فنی داخلی در UI اصلی نمایش داده نشود.
15. routeهای قدیمی مهم بدون صفحه شکسته به مقصد مناسب هدایت شوند.
16. تجربه در viewport موبایل بدون scroll افقی و با RTL صحیح کار کند.
17. تست‌های فعلی مرتبط پاس شوند و برای جریان اصلی تست جدید اضافه شود.
18. صفحه تقویم grid واقعی ماه، navigation، انتخاب روز، event detail و تغییر تاریخ را پشتیبانی کند.
19. نمای هفته و فهرست تقویم از همان داده واقعی eventها استفاده کنند.
20. تب `Engine` workflow پروژه یا run انتخاب‌شده را با node، edge و وضعیت واقعی نمایش دهد.
21. مسیر فعال، مرحله در حال اجرا، نیازمند اقدام و خطا در Engine قابل تشخیص باشند.
22. انتخاب node در Engine پنل جزئیات و لینک به آیتم مرتبط را باز کند.
23. Engine با React و componentهای موجود shadcn/ui پیاده‌سازی شود و از گراف hard-coded نهایی استفاده نکند.

## 17. خروجی مورد انتظار از عامل Cloud

در ابتدای کار:

1. ساختار فعلی Studio را بررسی کن.
2. فایل‌های اصلی و routeهای درگیر را مشخص کن.
3. یک برنامه اجرایی کوتاه ارائه بده.
4. سپس تغییرات را مرحله‌ای پیاده‌سازی کن.

در پایان کار گزارش بده:

- چه صفحات و componentهایی تغییر کردند
- چه چیزهایی حذف، ادغام یا redirect شدند
- چه تصمیم‌هایی به‌دلیل محدودیت معماری تغییر کردند
- چه تست‌هایی اجرا شدند و نتیجه چه بود
- چه مواردی، اگر وجود دارد، هنوز باقی مانده است

## دستور نهایی

هدف این پروژه «کم‌کردن تعداد کلیک‌ها» به‌تنهایی نیست؛ هدف این است که رابط بر اساس واحدهای واقعی کار کاربر ساخته شود. پروژه فقط context است. تجربه اصلی باید ساخت کانسپت، تبدیل آن به محتوا، جمع‌کردن محتوا در خروجی و برنامه‌ریزی خروجی باشد.

هنگام تصمیم‌گیری بین نمایش جزئیات بیشتر و حفظ تمرکز، تمرکز روی اقدام بعدی کاربر را انتخاب کن.
